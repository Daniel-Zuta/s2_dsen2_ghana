# agents.md

## Project

Jupyter notebooks for super-resolution of Sentinel-2 satellite imagery, following the **DSen2** methodology (Lanaras et al., "Super-resolution of Sentinel-2 images: Learning a globally applicable deep neural network").
Reference implementation: https://github.com/lanha/DSen2

Goal: upsample Sentinel-2's 20m and 60m bands to 10m resolution using a CNN trained with residual learning, guided by the native 10m bands (B2, B3, B4, B8).

## Methodology (from DSen2)

- Two separate networks (or one combined pipeline): one upsamples 20m→10m bands, another 60m→10m bands.
- Residual learning: the network predicts the high-resolution residual added to a simple upsampled (e.g. bicubic) version of the low-res band, not the raw pixel values.
- Trained on real Sentinel-2 tiles — inputs are downsampled to simulate the resolution gap, with the original band serving as ground truth (Wald's protocol).
- Bands:
  - 10m native: B2, B3, B4, B8
  - 20m → super-resolved: B5, B6, B7, B8A, B11, B12
  - 60m → super-resolved (optional): B1, B9
- Original reference stack: TensorFlow/Keras, NumPy, scikit-image, GDAL for geospatial I/O.
- Network itself is framework-agnostic: a small fully-convolutional residual CNN (VDSR-style — a few 3x3 conv layers + PReLU, global residual connection adding a bicubic-upsampled input back to the predicted output). No TF/Keras-specific mechanics involved.

## Framework decision

**PyTorch**, not the original TensorFlow/Keras.

- Why: the architecture ports directly (see above) and PyTorch fits better into the current geoAI ecosystem (torchgeo, rasterio-based pipelines) this project's output feeds into.
- Trade-off accepted: the original repo's pretrained `.hdf5` weights are Keras-specific. Reusing them would require manually converting weights layer-by-layer into the PyTorch model. Default plan is to train from scratch on our own data rather than do that conversion, unless a later need for the exact pretrained model comes up.

## Scope decision

**Train from scratch in PyTorch on our own data**, not porting/wrapping DSen2's original pretrained weights.

- Licensing: the DSen2 repo is **GPL-3.0**. Reusing its pretrained weights (or code) would pull that copyleft into anything built on top. A clean-room PyTorch reimplementation of the published *methodology* avoids that entanglement.
- Feasibility: DSen2's training is self-supervised (Wald's protocol) — low/high-res pairs are synthesized by downsampling real bands, so no external labels are needed. Sentinel-2's ~5-day revisit means our AOI/season window alone (see Study area below) already yields plenty of scenes/patches to train on.
- Risk avoided: porting Keras weights to PyTorch requires care around conv weight layout and numerical verification against the original outputs — real effort with failure modes that are easy to miss silently. Not worth it for the payoff here.
- Keep as a documented fallback only: if from-scratch results underperform, revisit porting the original weights as an initialization, with the licensing trade-off explicitly re-evaluated at that point.

## Data source decision

Originally planned to pull tiles via Google Earth Engine, but GEE's recent token/quota restrictions make that unreliable for this workflow. Using open, script-friendly STAC catalogs instead:

- **Microsoft Planetary Computer (primary choice)** — `sentinel-2-l2a` STAC collection, free signed access via `pystac-client` + `planetary-computer` Python packages (signing is handled transparently, no manual OAuth/credential setup). Also exposes the Scene Classification Layer (SCL) and a cloud-probability collection, both useful for building clean composites.
- **AWS Earth Search (Element84)** — fallback option. Public STAC API over the Sentinel-2 COGs bucket, zero auth required, but thinner cloud-masking metadata than Planetary Computer.
- **Copernicus Data Space Ecosystem (CDSE)** — official successor to the old Copernicus Open Access Hub; has both L1C and L2A, but OAuth/S3 credential setup is more involved than the above two. Consider only if PC/Earth Search prove insufficient.

Defaulting to **L2A** (surface reflectance) rather than the original paper's L1C: the super-resolution task only needs all bands present at native 10/20/60m resolution, and L2A is more directly useful for the downstream geoAI pipeline (no separate atmospheric correction step needed later).

## Study area

- **AOI**: Ghana (national extent for now). Sentinel-2 tiles over Ghana span UTM zones 30N and 31N.
- **Time range**: dry season composite, **January–May 2025**.
- **AOI filtering is two-stage, by design**: the STAC search itself (`stac.search_scenes`) uses a generous rectangular bbox (`config.GHANA_BBOX`) as a cheap superset — it deliberately overshoots into ocean/neighboring countries rather than risk missing edge coverage. Precision comes from a second, local step: `stac.filter_by_aoi` intersects each returned scene's actual footprint against Ghana's real admin-0 boundary (fetched once via OSM Nominatim, cached at `config.GHANA_BOUNDARY_PATH` — see `s2sr.boundaries`) and drops scenes whose overlap is below `config.MIN_AOI_OVERLAP_FRACTION`. This was discovered necessary empirically: the first bbox-only search over Ghana returned scenes across 53 MGRS tiles, several with near-zero real overlap (tiles that only clip the bbox corner). Keeping the search query itself unchanged (not narrowing to `intersects=<polygon>`) means the network search step never needs to be redone when the AOI is retuned — only the local filtering/downstream cells do.
- **Caveat**: Dec–Feb in this region also carries Harmattan dust haze from the Sahara. It won't be flagged by standard cloud masks (SCL / cloud-probability), but it degrades optical clarity. The compositing notebook should account for this beyond simple cloud-percentage filtering (e.g. percentile compositing, or haze-sensitive band ratio checks) rather than assuming SCL/cloud-probability alone is sufficient.
- **Training data scope**: Ghana-only for now. Deliberately not broadening to other regions yet — revisit once the Ghana pipeline works end-to-end.

## Patch sampling strategy

Training is self-supervised (Wald's protocol), so patch volume isn't the constraint — scene quality and diversity are. Approach:

1. **Scene selection** — query Planetary Computer for `sentinel-2-l2a` over the Ghana bbox, Jan–May 2025. Coarse-filter on `eo:cloud_cover` (e.g. <20%), then compute actual cloud+shadow+snow fraction from the SCL band *within the Ghana AOI* (tile-level metadata covers the whole granule, often mostly irrelevant area). Keep the best scene from a few different time windows per MGRS tile rather than just the single clearest scene overall, for some phenological/illumination variation. Add a secondary haze check (e.g. NDVI or blue-band reflectance relative to the scene's own distribution) since Harmattan haze isn't flagged by SCL.
2. **Spatial / land-cover stratification** — Ghana spans ~9–12 MGRS tiles (UTM 30N/31N). Draw patches from all passing tiles, and stratify across land-cover types (savanna, forest, cropland, coastal/Lake Volta water, urban) via a quick NDVI or ESA WorldCover bucketing, so the model doesn't overfit to whichever land cover is spatially dominant.
3. **Patch extraction** — align 10m/20m(/60m) bands to a common 10m grid, tile into fixed-size patches (~128×128 px at 10m is a reasonable practical size — more spatial context than DSen2's original small patches, still cheap for many samples per scene). Apply Wald's protocol per patch: downsample by the target factor (2× for the 20m network, 6× for the 60m network) using proper low-pass + decimate, not nearest-neighbor. Drop patches that are majority no-data, pure water, or still haze/cloud-contaminated after scene-level filtering.
4. **Train/val split by scene, not by patch** — hold out 1–2 whole MGRS tiles (or a date subset) for validation. Never split randomly at the patch level; adjacent patches from the same scene are spatially correlated and inflate validation scores.
5. **Augmentation** — random flips/90° rotations only (spectral relationships are orientation-invariant). No color/spectral augmentation — exact band ratios matter for the task.

## Repo status

Scaffolded, pipeline not yet implemented. Current structure:

- `notebooks/01_data_prep.ipynb` — Planetary Computer STAC search over Ghana (Jan–May 2025), coarse `eo:cloud_cover` filter, then local AOI tightening against Ghana's real boundary (see Study area above), saves the scene list to `data/interim/s2_scenes_ghana_2025_dry_season.geojson` (657 scenes / 41 tiles as of the last real run).
- `notebooks/02_scene_selection.ipynb` — loads notebook 1's output, re-searches STAC for live signed asset URLs, computes per-AOI SCL cloud/shadow/cirrus/snow fraction *and* SCL nodata fraction and a per-tile blue-band haze z-score for every scene (decimated raster reads, checkpointed to `data/interim/s2_scenes_ghana_2025_quality.geojson` since it's the expensive step — note the checkpoint is saved *before* the haze z-score columns are computed, so it won't have `is_haze_outlier`), filters on all three, then keeps the best scene per MGRS tile per month, plus a true-color eyeball check on the highest-blue-reflectance survivors. Saves to `data/interim/s2_scenes_ghana_2025_selected.geojson`. Thresholds (`MAX_SCL_CLOUD_SHADOW_FRACTION`, `MAX_SCL_NODATA_FRACTION`, `HAZE_ZSCORE_THRESHOLD`, `SELECTION_TIME_WINDOW` in `config.py`) are starting points meant to be retuned after inspecting the histograms this notebook plots — retuning only requires re-running from the filter/select cell onward, not the raster loop (a nodata-fraction filter added after the fact does need the raster loop re-run once, since that column didn't exist in earlier checkpoints).
- `notebooks/03_patch_extraction.ipynb` — loads notebook 2's selected-scenes output, re-searches STAC for live signed URLs, and extracts aligned native-resolution patches per scene via `s2sr.patches.extract_patches_for_scene`: `hr_10m` (4 x 128 x 128, B02/B03/B04/B08) and `hr_20m` (6 x 64 x 64, B05/B06/B07/B8A/B11/B12, co-located with the `hr_10m` patch), each candidate checked against the real Ghana boundary (`MIN_PATCH_AOI_COVERAGE`), SCL nodata fraction (`MAX_PATCH_NODATA_FRACTION`), and SCL cloud/shadow fraction (`MAX_PATCH_UNUSABLE_FRACTION`) before being kept, capped at `MAX_PATCHES_PER_SCENE` per scene. Saved as one `.npz` per patch under `data/processed/patches/`, manifest at `data/processed/patches_manifest.csv`. **Wald's-protocol downsampling is deliberately not done here** — patches are saved at native resolution, and the (input, target) training-pair construction happens later so the downsampling method can be changed without re-extracting patches. Structured as scene → 5-scene batch (with a timing estimate for the full run) → full run, given real windowed raster reads are much slower than notebook 2's decimated stats reads. **Resumable, for the same bandwidth reason as notebook 2's raster cache**: `extract_patches_for_scene` skips any patch already saved on disk (checked before doing any of the validity-check reads) and short-circuits entirely — zero network calls, not even to open the band files — for a scene that already has `MAX_PATCHES_PER_SCENE` patches saved. Validity stats (`aoi_coverage`, `nodata_fraction`, `unusable_fraction`) are stored inside each patch's `.npz` specifically so a reused patch's manifest record can be reconstructed from disk alone. Known gap: a scene with fewer possible valid windows than `MAX_PATCHES_PER_SCENE` has no persisted "already exhaustively searched" marker, so it re-scans (but doesn't re-download already-saved patches) on every rerun — harmless, just not fully free for that scene.
- **Gotcha: cloud/shadow fraction alone doesn't catch partial-swath nodata gaps.** Sentinel-2's orbit doesn't always fully cover a 100x100km MGRS tile in one pass, leaving a large nodata triangle in some scenes. `cloud_shadow_fraction` excludes nodata pixels from its own denominator (by design, to avoid nodata masquerading as cloud) — so a scene that's half nodata and cloud-free in the small valid remainder scored a "perfect" 0.0 and passed the filter. Caught via the eyeball check: 3 of 6 previewed scenes were roughly half solid black. Fixed by tracking `nodata_fraction` as a genuinely separate metric (`quality.scl_stats`, `MAX_SCL_NODATA_FRACTION` at the scene level; the equivalent check also exists per-patch in `patches.py` via `MAX_PATCH_NODATA_FRACTION`) rather than folding it into the cloud/shadow number. Any new per-AOI raster quality check should keep nodata accounting separate from whatever else it's measuring, for the same reason.
- **Open caveat, not yet fixed:** the haze z-score (`blue_reflectance_in_aoi`) averages blue reflectance over the *whole* AOI-intersecting area, including water. A bright lake/reservoir in frame can dominate that average and get flagged as "high blue reflectance" even when the scene shows no visible haze — seen in the eyeball check (a `30PZT` scene with a reservoir, clearly not hazy, had the highest blue_mean in the selected set). The haze detector may therefore be responding to water bodies as much as to actual atmospheric haze. A cleaner version would mask out water (SCL class 6) before averaging — not implemented yet since it requires reading SCL and B02 together rather than as separate functions.
- Land-cover stratification is not implemented yet — patches are currently sampled randomly within the AOI/SCL constraints, not stratified by land-cover class. Revisit if training results look skewed toward whichever land cover is spatially dominant.
- All notebook cells use explicit stable `id`s (not left to positional defaults) so future edits don't silently shift or overwrite neighboring cells — a real bug hit once during development. When creating or restructuring notebooks, always set explicit `id` fields. Also watch for VS Code save conflicts: if a notebook is open in the editor while it's edited externally, VS Code's stale in-memory buffer can silently overwrite the edit on its next save — this happened once too. After an external edit to an open notebook, close the tab without saving and reopen (or Revert File) before trusting what's on disk.
- `data/raw/`, `data/interim/`, `data/processed/` — gitignored except for `.gitkeep`; nothing committed here, ever (this includes `data/processed/patches/` and `patches_manifest.csv`).
- `data/boundaries/` — the one exception to the data-gitignore rule: small reference vector files (e.g. `ghana_adm0.geojson`), not imagery, so these are tracked.
- `models/` — gitignored except for `.gitkeep`; trained weights/checkpoints go here, never committed.
- `notebooks/04_train.ipynb` — loads `data/processed/patches_manifest.csv`, splits by `scene_id` via `s2sr.dataset.train_val_split_by_scene` (never by patch — see "Patch sampling strategy" point 4), builds Wald's-protocol (input, target) pairs on the fly via `s2sr.dataset.WaldPairDataset`, and trains `s2sr.model.DSen2Net20m` (L1 loss, Adam, `torch.amp` mixed precision — a no-op on CPU, so the same cell runs unchanged locally or on RAILS). A `SMOKE_TEST` flag near the top switches between a small local CPU sanity run (few scenes, few epochs) and a full run (all scenes, more epochs, larger batch) — meant to be smoke-tested locally against the existing local `patches_manifest.csv` before spending RAILS GPU time. Saves the best (lowest val-loss) checkpoint to `models/dsen2_20m.pt`. Only the 20m→10m branch is implemented; 60m bands (B01/B09) aren't extracted by `patches.py` at all yet.
- `src/s2sr/model.py` — `DSen2Net20m`: PyTorch, clean-room reimplementation (not a weight port — see Scope decision) of DSen2's VDSR-style residual CNN. `forward(guide, upsampled)` takes native-resolution 10m bands and a bicubic-upsampled 20m input (same H/W), concatenates them, runs a stack of `Conv2d`+`PReLU` blocks, and adds the result back onto `upsampled` as a residual correction.
- `src/s2sr/dataset.py` — `WaldPairDataset`: turns one native-resolution patch (`hr_10m`, `hr_20m` from `patches.py`) into one Wald's-protocol training pair — degrades `hr_10m`/`hr_20m` by `config.DOWNSAMPLE_FACTOR_20M` (Gaussian blur sized to the factor's FWHM, then decimate — avoids the aliasing a naive strided downsample would introduce), bicubic-upsamples the degraded 20m back up, and returns `(guide, upsampled, target)` where `target` is the *real* `hr_20m` (genuine ground truth, never simulated). Also `train_val_split_by_scene`.
- `src/s2sr/` — shared package: `config.py` (AOI bbox, boundary path, date range, STAC constants, band groups, quality-filter thresholds, patch-sampling constants, `RASTER_CACHE_DIR`), `stac.py` (Planetary Computer search + AOI-overlap filter helpers, `fetch_item_by_id` + `refresh_item` — see gotcha below), `boundaries.py` (fetches + caches country boundaries from OSM Nominatim), `raster.py` (decimated, disk-cached COG reads for scene-level stats — see caching note below — RGB preview helper), `quality.py` (`scl_stats`: SCL cloud/shadow fraction + nodata fraction from one read, haze z-score, SCL class constants), `patches.py` (native-resolution patch extraction with AOI + SCL nodata + SCL cloud/shadow validity filtering — not yet cached, see below), `model.py` + `dataset.py` (see notebook 4 above). Notebooks import it via `sys.path.insert(0, str(Path.cwd().parent / "src"))` — see the pattern in `01_data_prep.ipynb`.
- **Local raster cache (`data/interim/raster_cache/`, bandwidth is a real constraint — user's home connection is a mobile hotspot).** `raster.read_band_decimated_cached(item, band, out_size, resampling)` is memoized to disk via `joblib.Memory` (in `raster._read_band_decimated_by_id`), keyed on `(item_id, band, out_size, resampling)` — deliberately not on a signed href, which changes on every re-fetch. `quality.scl_stats` and `quality.blue_reflectance_in_aoi` (and transitively `raster.read_rgb_preview`) all go through this now, so notebook 2 reruns hit disk instead of re-downloading. Chose `joblib.Memory` over a hand-rolled `.npz` cache specifically because it hashes the *decorated function's own source* as part of the cache key — a future edit to the read logic auto-invalidates old entries, rather than silently serving stale results (a real weakness an earlier hand-rolled version had). Remaining trade-offs: no expiry (fine here — Jan–May 2025 imagery is historical and won't change); a warm cache silently skips the network path, so re-verifying a network-related fix (like `refresh_item` below) needs either a scene not yet cached or a manually cleared cache (`data/interim/raster_cache/`); joblib's source-hashing covers the decorated function's own body but doesn't follow into functions it calls, which is exactly why the read logic is inlined directly into `_read_band_decimated_by_id` rather than delegating to a separate helper. **Not yet applied to `patches.py`** (notebook 3's full-resolution windowed reads) — a similar cache there is a reasonable future addition once patch extraction is actually run.
- **Gotcha: `Resampling.average` is wrong for a categorical band.** The decimated-read caching work above surfaced this: `_read_band_decimated_by_id` used `Resampling.average` for every band, including SCL — but SCL values are class codes (0=nodata, 4=vegetation, 6=water, 8=cloud, ...), and numerically averaging them near a class boundary can produce a value that matches no real class, or worse, coincidentally matches a *different* class's code. Fixed by making `resampling` a parameter (default `Resampling.average`, correct for continuous reflectance bands) and having `quality.scl_stats` explicitly pass `Resampling.mode` (majority vote) for its SCL read. Any new decimated read of a categorical band should do the same — check whether the band is categorical before assuming `average` is fine.
- **Gotcha: Planetary Computer signed URLs expire, and re-signing an already-signed href in place is unsafe.** `items_by_id` dicts get built once near the top of a notebook and reused much later — by then the SAS tokens on those items' asset hrefs can be stale, and opening them raises a `RasterioIOError` wrapping an HTTP 403. The first fix attempt (`planetary_computer.sign(item)` on the existing item) made this *worse* — items from `catalog.search()` are already signed once via `sign_inplace`, and re-signing an href that already carries a SAS token query string isn't guaranteed to cleanly replace it, producing a genuine 403 in practice. The actual fix: `stac.refresh_item(item)` re-fetches the item fresh from STAC by id (`search(ids=[item.id])`), going through the exact same proven-working `search()` + `sign_inplace` path rather than mutating an existing href. Every function that reads assets from an `item` parameter (`quality.scl_cloud_shadow_fraction`, `quality.blue_reflectance_in_aoi`, `raster.read_rgb_preview`, `patches.extract_patches_for_scene`) calls this as its first line. Any new function that reads item assets should do the same — and if extending `refresh_item` itself, re-fetching (not in-place re-signing) is the safe pattern to keep. `get_catalog()` caches its client (module-level `_catalog`) rather than reopening one per call — `refresh_item` calling it in a loop otherwise means a fresh HTTP round-trip per item, each one an unnecessary chance for a network stall to hang (nothing in this stack has a configured timeout, so a stall hangs rather than errors — a kernel freeze during the eyeball-check loop was traced to this).
- **Gotcha: `gpd.read_file()` on a saved GeoJSON can silently change column dtypes.** GDAL's GeoJSON driver auto-detects field types from values — a `datetime` property written as an ISO string (e.g. from STAC item properties) can come back from `gpd.read_file()` as a pandas `Timestamp`, not a string. Code that assumes string operations (`row["datetime"][:10]`) on a column loaded this way will break with `TypeError: 'Timestamp' object is not subscriptable` — hit once in `02_scene_selection.ipynb`'s eyeball-check cell. Always wrap with `pd.to_datetime(...)` before formatting/slicing a datetime-like column that came from a loaded GeoJSON, regardless of what type you expect it to be.
- **Gotcha: save cells assumed their output directory already existed.** `data/interim/` and `data/processed/` are gitignored, so a fresh clone (e.g. onto a different machine/cluster) doesn't have them on disk at all — only `data/boundaries/` survives a clone, since it's the tracked exception. The `df.to_file(...)` / `.to_csv(...)` calls in `01_data_prep.ipynb` (`save-output`) and `02_scene_selection.ipynb` (`save-quality-checkpoint`, `save-selected`) worked locally only because those directories happened to already exist from earlier runs, and failed with a GDAL `DataSourceError` ("No such file or directory") the first time the repo was cloned fresh onto RAILS (see Compute environments below). Fixed by adding `out_path.parent.mkdir(parents=True, exist_ok=True)` immediately before each save call. `patches.py`'s `extract_patches_for_scene` already did this correctly (`out_dir.mkdir(parents=True, exist_ok=True)` at the top), so notebook 3's save cells were unaffected. Any new cell/function that writes to a gitignored data path should create its parent directory itself rather than assuming it exists.
- `environment.yml` — **primary** environment definition. Conda (`conda-forge` channel), Python 3.11 pinned (avoids wheel-availability gaps for GDAL-dependent packages like rasterio on very new Python versions), PyTorch via pip inside the conda env. User's workflow: `conda env create`, register the env as a Jupyter kernel via `ipykernel`, run notebooks in VS Code against that kernel.
- `requirements.txt` — plain-pip fallback, kept in sync with `environment.yml`'s package set but not the primary path.

## Compute environments

Two separate machines run this repo, kept in sync via git/GitHub (`git clone`/`git pull`) — **not** via file transfer, since `data/**` and `models/**` are gitignored (see above) and are regenerated independently in each environment rather than copied between them:

- **Local (Windows, miniconda)** — the primary dev environment; see `environment.yml` above. Used for day-to-day notebook work and small runs. Bandwidth-constrained at times (home connection is a mobile hotspot), which is why the disk caching/resumability described elsewhere in this doc (raster cache, resumable patch extraction) matters here specifically.
- **RAILS (NCSA/UIC HPC via Open OnDemand JupyterLab, `rails09`)** — used for GPU-heavy work (training, notebook 4+) on an A100 80GB. Python env is the pre-provisioned `conda/pytorch` module (`/sw/external/conda/pytorch`, PyTorch 2.6.0+cu124, confirmed CUDA-working), extended with `pip install --user` for the STAC/geospatial packages it didn't already have (`pystac-client`, `planetary-computer`; `geopandas`/`rasterio`/etc. were already present from prior GeoAI work in that same env). Its one registered Jupyter kernel (`jupyter kernelspec list` → `python3`) already points at this env, so no separate kernel registration was needed. Bandwidth is not a constraint here (university network) — notebooks 1–3 are re-run from scratch on RAILS rather than transferring the locally-generated `data/interim/`/`data/processed/` outputs over.

## Conventions for agents working here

- Use PyTorch for model/training code (see Framework decision above), not TensorFlow/Keras.
- Fetch Sentinel-2 tiles via STAC (Planetary Computer / CDSE / Earth Search), not the Earth Engine Python API (see Data source decision above).
- Prefer factoring reusable logic (data loading, patch extraction, PSNR/SAM metrics, band resampling) into plain `.py` modules imported by notebooks, rather than duplicating code across notebooks.
- Keep notebooks focused: one notebook per stage (e.g. data prep, training, inference/evaluation) rather than one monolithic notebook.
- Do not commit satellite imagery, model weights, or other large binary artifacts — use `.gitignore` and note expected data sources/paths in markdown cells instead.
- When implementing model/training code, stay consistent with the DSen2 paper's approach (residual learning over bicubic-upsampled input, Wald's protocol for train/test band downsampling) unless the user explicitly asks for a different method.
- Note actual band/resolution values (10m/20m/60m) explicitly in code and docs — don't assume generic image super-resolution conventions.
